# Integrating Pith UI

Use the exact published package and commit its lockfile. Import parts and types from `pith-ui` and the stylesheet from `pith-ui/styles.css`. Read the installed declarations, AI.md and APP.md. There are no scene, application or recipe subpath exports.

Compose opaque child handles into the documented native layout parts. The library controls typography, spacing, color, dimensions, motion and icons. Supply only content, finite semantics, state and callbacks. The only DOM input is one ordinary mount container; never inspect or style library output.

For Desk regions, copy the matching executable blueprint from `examples/assemblies` into the application's own source. The assembly documents give the exact part tree, update/reset policy, callback wiring and teardown. Preserve existing business controllers, native capabilities and target/revision checks. Do not copy old HTML/CSS or create another shared whole-scene API.

Every child belongs to one parent. Replace children through part methods; unchanged handles preserve focus and selection, and removed children are destroyed. Mount the shared Frame once and retain its owner for appearance and final destruction. Use supported disposal callbacks to retire application coordination before child cleanup. Explicit resets replace drafts; ordinary updates preserve them.

Use the parts-only showroom to inspect legal component states and specifications. Large combinations remain in internal regression scenes and executable assembly documentation. Internal baseline fixtures retain old assertions while the published package contains only the new parts dependency graph.

The application owns data, requests, persistence, permissions, credentials, file acquisition and native operations. Native pointer coordinates in a drop payload are incoming event data, never configurable presentation. Copy, download, local-link and image callbacks retain existing host validation and cancellation.
